## Contrato funcional del login

La lógica de autenticación debe funcionar así:

1. Recibir `username` y `password`.
2. Buscar el usuario por `username`.
3. Verificar que el usuario exista y esté habilitado.
4. Obtener la contraseña vigente desde `auth.historial_contrasena`.
5. La contraseña vigente se define como el último registro del usuario ordenado por `fecha_creacion DESC, id DESC`.
6. Comparar el password ingresado con ese `hashed_password` usando bcrypt.
7. Si el usuario no existe, la clave es inválida, el usuario está deshabilitado, o no tiene historial de contraseñas, responder con error controlado.
8. Si el login es correcto, el backend debe generar un JWT. El frontend recibirá la sesión mediante **Cookies HttpOnly** (no en el body) y un JSON con los datos del usuario y sus permisos en un array plano de strings (ej: `["pacientes:read", "turnos:create"]`). El backend debe configurar `CORSMiddleware` con `allow_credentials=True`, y el cliente HTTP del frontend debe incluir `withCredentials: true` en todas las peticiones.
9. Registrar siempre el intento en `auth.login`, con `username_ingresado`, `ip`, `exito` y `razon_fallo` cuando aplique. Para obtener la IP, el backend debe leer primero las cabeceras `X-Forwarded-For` o `X-Real-IP`, usando la IP directa solo como fallback.

### Errores visibles en UI y Códigos HTTP

La pantalla de login solo puede mostrar estos mensajes al usuario, determinados estrictamente por el status HTTP del backend:

- Si el usuario no existe, la clave es inválida o no tiene historial: devolver HTTP 401 y mostrar en UI `Credenciales incorrectas`.
- Si el usuario está deshabilitado: devolver HTTP 403 y mostrar en UI `Usuario deshabilitado`.

Si aparece un error, limpiá los campos de usuario y contraseña.

## Contrato de permisos y sidebar

El sidebar se gobierna por permisos `recurso:accion`, no por roles.

La base de control es:

- `auth.usuario` pertenece a un `auth.rol`
- `auth.rol` se conecta a `auth.permiso` mediante `auth.rol_permiso`
- El backend carga los permisos del usuario al iniciar sesión
- El frontend decide qué mostrar con esos permisos

### Regla de visualización

- Un grupo del sidebar se muestra si el usuario tiene al menos un permiso `:read` de ese grupo.
- El wildcard `*` muestra todos los menús.
- Los botones de acción se muestran u ocultan según el permiso específico.
- No uses matrices de rol en la UI.

## Reglas sobre configuración dinámica y Endpoints

La configuración dinámica vive en `sys.config`. No inventes otro schema ni renombres eso a `global.config`.

Reglas de consumo estrictas:
- **Expiración de Tokens (Backend):** La vigencia de sesión al crear el JWT se debe obtener con estas queries:
  - Access Token: `select parametro_valor from sys.config where config_id = 1 and parametro_id = 1;`
  - Refresh Token: `select parametro_valor from sys.config where config_id = 1 and parametro_id = 2;`
- **Branding UI (Frontend):** Crear un endpoint público (ej: `GET /api/config/public`) que devuelva el nombre de la clínica (Razón Social) usando esta query: `select parametro_valor as RazonSocial from sys.config where config_id = 2 and parametro_id = 1;`. La pantalla de login y el shell deben consumir esto.

## Reglas sobre historial de contraseñas

La contraseña vigente no está en `auth.usuario`.

Debe leerse desde `auth.historial_contrasena` con esta regla:

- filtrar por `usuario_id`
- ordenar por `fecha_creacion DESC, id DESC`
- tomar el primer registro
- usar su `hashed_password` como contraseña vigente

Si no hay historial para un usuario existente, el login debe fallar como credenciales inválidas.
